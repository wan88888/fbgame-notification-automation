# 自动推送平台 SOP

运营入口升级为 PushLoop。原来的 CSV 执行页面保留在「旧版执行工具」。

## 已实现与接入边界

| 环节 | 当前实现 |
| --- | --- |
| 文案生成 | 可配置 Chat Completions 兼容模型；传入游戏、语言、人群、活动信息与历史周报。未配置时明确提示；中英文模板可独立起稿，不标作 AI |
| 内容审核 | 每批次 1–6 个候选，编辑后恰好选择一条本周发送。每游戏每周一个批次 |
| CSV | 上传真实 Facebook 模板，替换对应语言标题/正文/label，保留图片、payload 等固定字段；下载内容、排期和运营计划 |
| Facebook 后台执行 | 复用 AdsPower / Playwright：导航、上传、日期与策略、Save、Turn On；开启后回读同一行 Turn Off |
| 每周二固定时刻 / 独立 Publish | **尚未接通自动化**。可保存时刻/时区；需运营在 Facebook 人工排期及 Publish 后填写核验。自动执行仅支持现有 Predicted Best Time |
| 效果回收 | 实际 CSV 导入或配置效果服务 GET 接口。没有内置 Facebook Insights 抓取，也没有自动建立游戏回流埋点 |
| 运营报告 | 真实量、加权率、观察窗口、数据缺口、跨周策略依据；Markdown 下载 |
| 下一轮 | 手动或定时生成下一周草稿，继承模板与历史建议；已配置 AI 时定时生成新候选。草稿仍需运营审核和执行 |

“执行完成”不等于“发送成功”。平台状态为：草稿 → 待执行 → 后台执行中 → 待核验 → 排期已核验 → 复盘已完成。失败有独立状态与操作轨迹。

## 第一次使用

1. 在仓库根目录安装依赖：`npm ci`、`npm --prefix apps/api ci`、`npm --prefix apps/web ci`。
2. 将 `.env.example` 所需配置填入本机 `.env`。AdsPower 需有已登录 Facebook 的 profile。不要把 API Key 放到前端代码或聊天中。
3. 分别运行 `npm run ops:api` 和 `npm run ops:web`，打开 `http://localhost:5173`。
4. 在「平台设置」选择默认游戏、语言、主题、人群、活动信息及时间策略。游戏映射来自 `campaigns/projects.json`。
5. 每周二固定时刻初始值为北京时间 10:00，可修改；实际需在 Facebook 核验。若选择最佳时间策略，日期按 **UTC**，不承诺固定时分。
6. 模型接入配置 `OPS_AI_URL`（完整 chat/completions 地址）、`OPS_AI_MODEL`、`OPS_AI_KEY`；重启 API。兼容服务必须返回 `choices[0].message.content` 中的文案 JSON。接口格式参考 [Chat Completions 官方文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)。模型失败不会覆盖已有草稿。

## 每周操作

1. **创建推送计划**：选择游戏和未来周二。重复的游戏/周次会阻断，使用已有批次继续处理。
2. **文案审核**：AI 或模板生成，编辑标题、正文，选择一条本周发送，然后保存。当前每天单条的约束沿用原执行器；其他候选不上传，供未来测试。
3. **导入 Facebook CSV 模板**：从已验证可用的导出表复制“表头 + 一条样例记录”。必须有 `label`、`notification_title_*`、`notification_body_*`。多语言模板需填写同语言的标题列、正文列；其他语言的文案单元格会留空，避免夹带旧文案。图片与 payload 等固定字段保留，请核对是否适用于本次活动。标题/正文的 80/500 字符上限是本平台的编辑限制，不代表 Facebook 的官方上限。
4. **校验并准备 CSV**：文件保存到批次独立目录。修改文案、模板或设置后必须重新准备。模板已提供只代表本地结构检查通过，Facebook 是否接受以实际后台为准。
5. **排期执行**：最佳时间模式可点执行，调用真实后台；固定时刻模式下载内容 CSV，在 Facebook 上传、设定日期/时刻/时区、开启通知、完成后台要求的 Publish。
6. **记录核验**：写明操作人、日期、策略、开启状态（固定时刻还包括时区、Publish 结果）。平台只标记“排期已核验”，不伪造送达状态。
7. **收集效果**：观察窗口结束后导入 CSV，或从效果接口同步。
8. **周报与下一轮**：生成报告，查看样本是否充足和历史建议，下载周报，创建下一周草稿。已创建的下一轮不会重复创建。

人群与活动信息用于文案和分析；**不会自动设置 Facebook 受众，也不会创建游戏内奖励**。

## 效果数据约定

```csv
label,sent,opened,clicked,recalled,recall_eligible,window_hours
这里填本批次已选文案的label,1000,120,50,20,500,144
```

以上数字仅用于说明格式，正式回填必须使用真实数据。

- `sent` 必填非负整数；`opened`、`clicked` 为对应窗口去重人数，不能超过发送量。
- `recalled` 为该文案归因的回流人数；`recall_eligible` 为对应可召回人数。回流需游戏埋点/数据服务提供；不能从点击量推导。
- 空值代表“未提供”，不是 0。分母为 0 或缺失时不计算比率。
- 打开率 = opened / sent；CTR = clicked / sent；召回率 = recalled / recall_eligible。总率按总分子 / 总分母计算。
- `window_hours` 为实际已完成的观察窗口。省略时默认 168 小时。循环自动化默认在 144 小时检查，建议在 CSV 显式填写 144，以便下周二之前复盘；可在平台调整自动复盘窗口。
- 固定时间模式从计划发送时刻起算；最佳时间模式保守地从该 UTC 日期末尾起算，避免未完整观察的数据进入报告。
- 未选中 label、未知 label、重复 label、负值、小数计数、未来窗口等会拒绝整次导入。重复导入覆盖，不重复累加。

效果接口配置为 `OPS_METRICS_URL`，平台通过 GET 请求附带 `batch_id`、`project_key`、`week_of`、`labels`、`window_hours`，可用 `OPS_METRICS_TOKEN` 配置 Bearer 鉴权。接口返回上述 CSV。它是供现有数据服务接入的合同，不是 Facebook 官方 API 的替代地址。

## 周报策略与定时循环

- 样本默认门槛为 100。缺失数据和样本不足明确显示，不虚构 Top/低表现排名。
- 当前单游戏单周仅发送一条，报告不会强行做“本周 A/B 排名”。跨周比较要求同项目、语言、人群、时区、发送模式、固定时刻（固定模式）及观察窗口。
- 保留/暂停规则要求同主题和其他主题各至少两个可比往周，本条与同主题往周相对其他主题加权基线持续有至少 20% 同方向差异。这是保守策略建议，不是统计显著性或因果结论。
- 打开「自动回收数据与生成周报」后，API 每 60 秒检查成熟批次；接口失败最多每小时重试，错误显示在批次/平台设置。
- 打开「复盘后自动创建下一周草稿」后，复制模板、采用历史建议；AI 可用时请求新文案，失败保留草稿和错误记录。非中英文语言需要 AI 生成。
- 自动化不会后台代替运营审批文案或点击 Publish。服务停止期间不执行；重启后恢复定时检查，错过的推送周期建立未来周二草稿，不补发过期通知。

## 失败处理

- 执行器部分成功、未处理条目、开启状态无法确认都报告失败。
- 服务重启不会自动重放可能已经生效的 Facebook 写操作。先去后台核验。
- 如果通知已存在但只需修正排期/开启，在核验说明中记录同 label 已存在，然后点击“仅重试编辑与开启”。续跑使用 `--no-upload`，避免重复上传；如后台不存在这条通知，请先用该批次下载的 CSV 人工创建。
- 如果已经在后台完成全部操作，可以直接记录核验，无需再执行。
- SOP 批次触及 active 上限时不会自动删除其他批次的 Completed 通知。先在后台处理名额再续跑。
- 旧版 CLI 的 `--dry-run` 仍可能上传 CSV；不要把它作为无副作用测试。本项目的自动化测试使用模拟的浏览器和网络，不连接 Facebook。

## 部署与数据

SOP 存储在 `.ops-console/sop/state.json`，CSV、排期输入和续跑记录在 `.ops-console/sop/artifacts/<batch-id>/`；执行日志在 `.ops-console/jobs/`。这些目录已被 Git 忽略，请按需备份。

当前采用本机文件持久化，适用于**单台执行机、单个 API 实例**，不要多实例同时写这些文件。API 默认监听 `127.0.0.1:8787`，前端代理 `/api`。团队、局域网或隧道访问前应设置强随机 `OPS_API_TOKEN`，运营在平台设置中输入令牌；该令牌为共享访问控制，不是多用户角色系统。自动化及 AI 调用需 API 进程持续运行；Linux 可沿用 `scripts/install-ops-services.sh` 的 systemd 服务，macOS 需自行配置持久进程管理。

检查命令：`npm run ops:check`（根代码/API 类型检查、前端构建、lint、全部测试）。所有新增页面已接入主入口；没有执行真实 Facebook 发布验收。

## 删除测试计划与回收站

选中当前批次后，状态标签旁提供「删除计划」。仅未执行的草稿或待执行计划可以删除，删除后进入顶部「回收站」，文案、模板和文件保留，支持恢复。恢复回到草稿，需要重新检查日期并准备 CSV。如果同游戏同周已新建其他计划，恢复会提示重复冲突。

已进入后台执行、失败后待核查或已核验的计划不能删除，以免丢失实际操作记录。删除本地计划不会取消 Facebook 后台已存在的推送；取消发送需在 Facebook 后台处理。删除自动生成的下一周草稿后，定时循环不会把它重新生成。

默认的 10:00 是计划时间，不是自动执行开关。仅新建草稿不会运行推送，也不会发飞书通知。当前 SOP 执行器显式关闭飞书结果通知；旧版执行工具仅在配置飞书 Webhook 且实际运行任务后才会发送运行结果。

## 运营易用性更新（2026-09-14）

- 工作台顶部按计划状态显示下一步，区分本地文件、执行记录、人工核验与导入的效果数据。取消的计划停止推进；已核验排期不等于实际送达。
- 推送计划支持按游戏、状态筛选，按游戏名称、日期、负责人搜索，分页查看。批量删除仅限未执行草稿，部分失败时明确显示结果；回收站可恢复。
- 「复制计划」继承原计划文案、模板、发送策略和负责人，重新生成标签，不继承执行任务、核验、效果或报告；必须选择尚无同游戏计划的未来周二。复制活动奖励文案后需复核有效期。
- 「编辑本计划策略」直接修改当前草稿，不再要求先改全局设置。保存后需重新准备 CSV。全局设置只作为新计划默认值。
- 「负责人」是协作标记，出现在列表与群通知里，不是登录身份、权限校验或自动 @ 个人。计划执行与角色权限仍使用现有平台机制。
- 文案有文字预览；编辑未保存时，轮询和负责人修改不会覆盖输入，离开网页会提示；重新生成文案有替换确认。
- 「执行前检查」核对计划状态、日期、文案与模板、生成文件，并对最佳时间模式只读查询 AdsPower 浏览器是否活动。结果有效期 5 分钟，执行时服务器再次检查。Facebook 登录账号、内容和奖励、日期时区由运营勾选确认，不会把浏览器连接当作登录成功。
- 固定时刻检查后依然需要下载内容 CSV / 运营计划，人工完成 Facebook 排期和核验；固定时刻不提供可执行排期 CSV。检查、预览、复制不会发布通知。
- 「取消计划」保留历史并停止自动复盘等后续处理。执行中不可取消，已执行计划需先在 Facebook 关闭或撤回，并在平台确认。平台取消和删除均不会操作 Facebook。
- 旧版执行工具保留左侧导航直接入口，位于「文案与排期」之后；高级设置中也保留快捷入口。技术接口配置收纳到「平台设置 > 高级设置」，CSV 多语言字段映射与原始日志默认折叠。执行结束后停止日志轮询。

### 飞书协作通知

在执行机 `.env` 配置专用 `OPS_FEISHU_WEBHOOK_URL`，如机器人启用签名则同时配置 `OPS_FEISHU_SIGN_SECRET`，重启 API。Webhook 支持飞书 / Lark 官方机器人 HTTPS 地址，密钥不会返回浏览器。SOP 不继承旧工具的 `FEISHU_WEBHOOK_URL`。

运营在「平台设置 > 飞书协作通知」填写接收群名称，开启并保存；群名称只是提示，实际接收方由管理员配置的 Webhook 决定。默认关闭，配置密钥本身不会开启消息发送。开启会把后续以下事件送到群：

- 未执行计划距离排期截止时间不足 24 小时或已过期（最佳时间模式以 UTC 日期开始为截止时间）（每计划提醒一次，不自动执行）。
- 后台执行失败、执行完成待人工核验、自动复盘异常。
- 周报生成、下一周草稿生成。

队列与发送结果保存在平台状态中，执行机每分钟检查；失败间隔 5 分钟重试，最多 3 次。一次最多处理 3 条。网络超时或进程中断可能造成重复通知；「机器人已接收」不表示群成员已读。通知不含原始错误日志或服务密钥。设置页可查看最近 50 条发送记录，失败仍可在平台处理原计划。

关闭通知会取消待发记录，不会补发关闭期间的历史事件；删除或取消计划也会取消其待发通知。机器人配置更换应先关闭通知、修改配置并重启，再重新开启，防止旧消息发到新群。服务停机期间无法发送提醒，重新启动后才继续检查，未到实际发布验收前应由运营跟进。

本次开发验证使用隔离计划与模拟消息接口，没有向真实 Facebook 或飞书发布消息。

### 回收站永久删除

回收站每条计划提供「恢复」和「永久删除」，顶部提供「清空回收站」。永久删除前会确认对象和数量，并提示不可恢复；删除该计划的文案、模板、操作与通知记录，以及本地生成的 CSV 等文件，不操作 Facebook。

清空按确认时的计划列表执行。列表中有计划被其他同事恢复时会拒绝操作，要求刷新；随后新移入回收站的计划不会被一并删除。清理失败会保留记录并显示失败项。若永久删除的是由周报生成的下周草稿，上周计划仅保留“下周草稿已永久删除”的操作标记，定时任务不会重新生成；重新安排请复制计划。
